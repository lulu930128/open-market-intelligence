## Decisions Made

- Treat crypto as a future isolated market domain, not an extension of stock-market decision workflows.
- Treat crypto live execution as a later explicit gate, after read-only realtime data and paper trading.
- Keep AI disconnected from crypto execution. Future AI, if any, must be advisory only.
- Use WebSocket-first collectors and in-memory latest state for tradeable data; use SQLite for bounded persistence and audit.
- First realtime implementation is WebSocket-first contract/parser/latest-state/source-health, with live connector startup enabled only for verified providers and `always_on` subscription items.
- `GET` crypto endpoints read local cache only. External provider fetches live behind explicit `POST .../refresh` endpoints.
- CoinGecko is context only and is not used as an execution-price source.
- Automatic trading is the final milestone. It must wait until backend crypto data coverage is complete and the full crypto frontend workflow is implemented and verified.
- No strategy, paper trading, live order placement, or execution logic is included in milestones 4-5.
- Resource/commodity data is a watch-only context domain. It is not a self-selected watchlist and has no trading or AI execution path.
- The resource/commodity sidebar starts with default pinned folders only: `虛擬貨幣` and `商品`.
- Commodity provider refresh is intentionally deferred until the data vendor is selected.

## Known Issues / Risks

- Current repo-level `AGENTS.md` says OMI is not an automatic trading system. A future implementation must either keep live execution outside OMI core or explicitly record a crypto-only exception with strict boundaries before any live order path is added.
- Provider API details, rate limits, authentication requirements, and WebSocket sequence semantics must be re-verified before enabling broader live collector coverage.
- OKX official docs did not render through the browser tool during this pass; current OKX REST/realtime adapters must be re-verified against OKX official docs before enabling OKX live WebSocket collection.
- Windows-local runtime and SQLite are acceptable for a local research/paper-trading workstation, but not for high-frequency trading or low-latency market making.
- Cross-exchange spread strategies can be misleading unless fees, slippage, inventory, transfer delays, withdrawal limits, and exchange-specific downtime are modeled.
- Current implementation includes an enabled-by-default WebSocket runtime manager for verified BitoPro/Binance `always_on` streams. OKX realtime remains disabled until official-doc re-verification.
- Current implementation does not include paper trading tables, strategy engine, or live execution audit/risk-gate tables.
- Current implementation includes read-only crypto frontend wiring, a first K-line chart pass, a Taiwan-style pinned left-sidebar crypto category, and a Taiwan-style right-side K-line/data split. Detailed frontend production polish remains: responsive browser QA, realtime-enabled mode indicators, and deeper empty/error/partial-state UX.
- Current resource/commodity implementation creates contract, catalog, quote cache, and OHLCV cache surfaces only. It does not fetch live commodity or FX data yet.
- Latest live check confirms crypto provider fetches are currently working, but this is a point-in-time probe, not a long-running uptime guarantee.
- Existing backend process on `127.0.0.1:8400` must be restarted before the new `/api/resource-market/*` routes are available there.
- Data-subscription settings are persisted, visible in SettingsDock, enforced by explicit crypto refresh APIs, used to build always-on realtime WebSocket stream specs, and trigger a controlled crypto realtime collector reload when settings are saved.
- Frontend live chart rendering now prefers SSE over the backend realtime latest-state API and falls back to bounded polling. It is still snapshot-based at a 1-second cadence, not a direct browser connection to provider WebSockets.
